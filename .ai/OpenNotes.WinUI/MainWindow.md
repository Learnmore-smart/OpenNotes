# OpenNotes.WinUI/MainWindow.xaml.cs
> Last updated: 2026-09-25 (window-scoped PenService — review fix) | Protection: STANDARD

## Purpose
WinUI 3 main-window code-behind (`Caelum.MainWindow : Microsoft.UI.Xaml.Window`, sealed partial). Ports the chrome + tab-model slice of the 2,094-line WPF `MainWindow.xaml.cs` plus the Task 5 home-facing surface: `SearchBox`/`SelectButton`/`SortButton`/`MoreButton` wired to the active `HomePage`, `ShowToast` overlay toasts, `NavigateActiveTabToFile` → `EditorPage` navigation, `HandleFilePathChanged` tab retitle/repath, the Settings/Check-for-updates/About flyout actions, and the Task 9 Phase A close/dirty protocol (save→release workflows for tab close, window close, navigation and same-tab file open).

## What It Does
- **Window chrome:** `InitializeAppWindow` resolves `AppWindow` via `WinRT.Interop.WindowNative` + `Microsoft.UI.Win32Interop`, sizes/centers **1280×720 DIPs scaled by `GetDpiForWindow(hWnd)/96`** — `MoveAndResize` AND `PreferredMinimumWidth/Height` take PHYSICAL pixels under PerMonitorV2 (WPF sizes were DIPs), so `GetWindowRasterizationScale` gives the true scale before the visual tree exists (verified: 200% → 2560×1440 first paint, no resize flicker). `RootGrid_Loaded` re-runs `SizeAndCenter` ONLY if `XamlRoot.RasterizationScale` ≠ the applied scale (first-paint race safety), then hooks `XamlRoot.Changed` → `ApplyMinimumSize` — cross-monitor DPI moves re-floor the minimum but NEVER re-size/re-center (user's size stays theirs); a `DidPresenterChange` swap also re-applies the minimum (a fresh presenter resets it). Sets `ExtendsContentIntoTitleBar=true` and `SetTitleBar(AppTitleBar)` so the 40px XAML title row is the real caption rect (`WM_NCHITTEST`→HTCAPTION verified). Caption buttons call `OverlappedPresenter.Minimize()/Maximize()/Restore()` and `Window.Close()`; `AppWindow.Changed` swaps the maximize/restore glyph (WPF `MainWindow_StateChanged` parity).
- **System caption removal (fix over `dbfd81a`):** `ExtendsContentIntoTitleBar` alone leaves the system Min/Max/Close rendered TOPMOST over the right edge — they occluded the custom caption buttons at identical rects (UIA Invoke smokes passed anyway since they bypass hit-testing; the real-pointer smoke was unknowingly clicking the system buttons). `ApplyCustomChrome` calls `OverlappedPresenter.SetBorderAndTitleBar(hasBorder: true, hasTitleBar: false)` — keeps the resize border/shadow, drops the system caption buttons so the XAML buttons are the only caption UI. Re-applied in `AppWindow_Changed` on `DidPresenterChange` (a presenter swap would silently restore system buttons).
- **Tabs:** `ObservableCollection<AppTab> _tabs` bound to the `TabStrip` ListView. `AddNewHomeTab` creates a `Frame` per tab (added to `TabContentArea`, only the active one `Visible`), navigates to `HomePage`, and activates on request. `ActivateTab` toggles `IsActive`/frame visibility, calls `EditorPage.SetHostActive(false)` on every deactivated tab's editor (`(true)` on the activated one — hidden tabs gate input + stop the marching-ants timer, WPF parity) and syncs `TabStrip.SelectedItem` under `_syncingTabSelection`. `CloseTab` is now the async T9 protocol (WPF parity): `_tabCloseWorkflows.Add(tab)` guards re-entry, the editor `PrepareForCloseAsync` saves the newest generation (dirty → `Main.FileAutoSaved` toast), then `ReleaseResourcesAsync` runs under a 30s `CloseWorkflowTimeout`; only success reaches `RemoveTabAfterResourcesReleased` (frame removal + last-tab Home recreation + `_tabs.Last()` activation). A timed-out release hands off to `ContinueTimedOutTabCloseAsync` — the workflow marker stays until the native release settles; failed prepares cancel prior preparations and leave the tab alive. `MoveTab` keeps the WPF insert-before/after index math for programmatic moves.
- **Tab strip input:** ListView single-selection → `ActivateTab` (guarded by `_syncingTabSelection` during programmatic changes and removal); drag-reorder needs `CanReorderItems`+`CanDragItems`+`AllowDrop` (mutates the bound collection in place; `MoveTab` is additionally guarded by `_syncingTabSelection` + re-asserts `TabStrip.SelectedItem` so a mid-move auto-select can't flip `_activeTab`); middle-click on a tab pill closes it; the close button consumes the left press (WPF `PreviewMouseLeftButtonDown` parity — no activate-then-close) and tags the pressed tab so a stale `Click` on a recycled container can't close the wrong tab; `CloseTab` nulls `tab.Frame` to release the page tree. `PointerExited` re-applies computed `TabBackground` (never `ClearValue` — x:Bind has no expression to restore).
- **Navigation (T9):** `NavBack`/`NavForward`/`NavHome`/`NavigateActiveTabToFile` all run the prepare barrier (`_navigationWorkflowActive` + 30s timeout) before touching `ActiveFrame` — WinUI destroys outgoing pages (no journal), so `EditorPage.PrepareForNavigationAsync` must persist first (dirty → `Main.FileAutoSaved`), then `SetHostActive(false)` + navigate. `NavBack_Click` additionally routes through Core `NavigationCloseCoordinator.TryNavigateBackAsync` (prepare → recheck `CanGoBack` → `CancelClosePreparation` if stale → navigate); WPF kept journal-resident editors so it only needed the coordinator for Back — Forward/Home/file-open prepares are WinUI-specific necessities. `Frame_Navigated` calls `SetHostActive(true)` + `ResumeDocumentInteraction()` on an `EditorPage` hosted by the active frame (reopens admission if a prepared editor ever survives), then refreshes nav state. `HandleFilePathChanged(old,new)` retitles/repaths every open tab of a renamed file (WPF parity) including the stub `EditorPage.UpdateCurrentPdfPath`.
- **Home toolbar (Task 5):** `HomeToolbarPanel` hosts `SearchBox` (TextChanged → `GetActiveHomePage()?.Filter`), `SelectButton` (→ `ToggleSelectionMode` + `RefreshSelectButtonVisualState` active pill + toast), `SortButton` (flyout `SortByNameMenuItem`/`SortByDateMenuItem` → `SortByName`/`SortByDate`), `MoreButton` flyout (`SettingsMenuItem` → `Settings_Click` → `OpenSettingsDialogAsync`, `CheckForUpdatesMenuItem`, `AboutMenuItem`). `UpdateActiveTabInfo` shows the panel only when `ActiveFrame.Content is HomePage` — editor stubs hide it.
- **Toast (WPF `ShowToast` parity):** `ShowToast(message, iconGlyph, durationMs)` animates `ToastBorder`/`ToastText`/`ToastIcon` opacity via `DoubleAnimation` (fade-in EaseOut, timed dismiss fade-out EaseIn, `CancellationTokenSource` resets between toasts); `MapToastIconGlyph` maps WPF icon names → Segoe MDL2 stand-ins.
- **Window-scoped pen service (2026-09-25 review fix):** exactly ONE `PenService` per window — `GetOrCreatePenService()` lazily constructs, subscribes (`ToolToggleRequested`/`PenDeviceDetected`) and `Initialize`s it on this HWND (idempotent call each access, so a not-ready HWND retries); `MainWindow_Closed` disposes it. Both events route ONLY to `_activeTab?.Frame?.Content as EditorPage` → `HandlePenToolToggle()` / `HandlePenDeviceDetected(info)` (the device toast is dropped when no editor tab is active — WPF `IsActiveEditorPage` parity); the editor re-gates on `_isHostActive`/`_resourcesReleased`. Per-EditorPage construction is FORBIDDEN — every page subclassed the same HWND and re-registered the same hotkey ids (duplicates fail; the owning tab's teardown killed it app-wide; every subclass proc saw the shared WM_HOTKEY so the toggle hit inactive editors).
- **Window close (T9, WPF `OnClosing` parity):** `_appWindow.Closing += AppWindow_Closing` — `_allowWindowClose` short-circuits the second pass; otherwise `args.Cancel = true`, `_windowCloseWorkflowActive` + `_windowCloseCts` (30s) start `CompleteWindowCloseAsync`: prepare EVERY live editor (`_tabs[].Frame.Content as EditorPage` — no journal), then release sequentially; `OperationCanceledException` mid-release hands off to `ContinueTimedOutWindowCloseAsync` (background continuation, workflow stays armed, a second close attempt is refused); all settled → `DispatcherQueue.TryEnqueue(Low, () => { _allowWindowClose = true; Close(); })` — the latch arms INSIDE the queued callback so a failed enqueue cannot leave the protocol bypassed (failure → `InvalidOperationException` → normal failure path). Failure cancels unprepared editors per-item via `TryCancelClosePreparation` (a faulted cancel can no longer strand `_windowCloseWorkflowActive`), removes tabs whose editors already released (no zombie tabs after a partial failure), keeps the window open, toasts `Editor.SaveFailed`.
- **Window file drop (Task 5 review fix):** `RootGrid` `DragOver`/`Drop` — `Window_DragOver` returns early when a `HomePage` is active (its grid owns drops; WPF `ShouldDeferWindowFileDrop` parity), else accepts `Copy` when `HasStorageItems`. `Window_Drop` → `GetDroppedImportablePathsAsync` → per file `TryImportDroppedDocumentAsync` (PDF passthrough; Word → `WordToPdfConverter` + converting toast + `WinUiDialogService` errors — WPF's `Mouse.OverrideCursor` wait has no WinUI port: `UIElement.ProtectedCursor` is protected and `Window` can't set it) → `OpenFileInNewTab` per result (WPF `Window_Drop`/`OpenFileInNewTab` parity).
- **More-menu actions:** `Settings_Click` → `OpenSettingsDialogAsync` (T9-B): loads the persisted settings, shows `SettingsDialog` (the WPF `SettingsWindow` port) under `RunUnderDialogGateAsync`, on confirm runs `ApplySettings` (`AppSettingsService.Save` → `PreviewSettings`) + `Main.SettingsSaved` toast; on cancel `PreviewSettings(originalSettings)` re-asserts the restore (the dialog's own `Closed` handler already reverted the live preview). `PreviewSettings(AppSettings)` (public — the dialog drives it for live preview) applies language + theme/backdrop (`WinUiThemeService.Apply`) and `editor.ApplySettings(settings)` on every open tab's `EditorPage`. `CheckForUpdates_Click` — serialized via `_isUpdateCheckInProgress`, `_updateCheckCts` cancels on window close; `UpdateCheckService.CheckAsync(installed)` → up-to-date info dialog, or confirm → `OpenTrustedReleasePage` (validated by `UpdateCheckService.IsTrustedReleaseUri`, `UseShellExecute`); `UpdateCheckException.Kind` maps to localized failure messages (`GetUpdateCheckFailureMessage`). `About_Click` → localized info dialog. All dialogs go through `WinUiDialogService` with `RootGrid.XamlRoot`.
- **Startup:** `AppSettingsService.Load()` → `WinUiThemeService.Apply(theme, workspaceBackdrop)` + `LocalizationService.ApplyLanguage`, `WinUiThemeService.RegisterWindow(this)` + `ThemeApplied` → `AppTab.RefreshVisualState()` so tab pills re-resolve palette brushes.
- **Keyboard (WPF parity):** Ctrl+T new tab, Ctrl+W close active, Ctrl(+Shift)+Tab cycle — on `RootGrid.PreviewKeyDown` via `InputKeyboardSource.GetKeyStateForCurrentThread`. **Task 6:** Ctrl+F forwards to `editor.OpenSearchPanel()` when the active frame hosts an `EditorPage` — the WPF shell treats it as a window-level accelerator, so it must reach the editor regardless of which chrome element holds focus.
- **Debug seam (DEBUG only):** `--tabsmoke` runs `RunTabSmoke` ~800ms after activation — adds two tabs, activates, `MoveTab` first→end, closes one, appends a state log to `%TEMP%\opennotes_winui_tabsmoke.log` for automation-free environments. `TabCount`/`Tabs`/`ActiveTab` internals expose state.

## Important Notes / NEVER Change
- NEVER remove `ApplyCustomChrome` / the `SetBorderAndTitleBar(true, false)` call and NEVER skip re-applying it in `AppWindow_Changed` on `DidPresenterChange` — without it the system caption buttons render topmost over the custom Min/Max/Close and real clicks hit the system buttons, not ours (regression verified: two UIA button sets coexisted at identical rects before the fix).
- `CloseTab` is async-void by design (WPF parity) — NEVER remove the tab before `ReleaseResourcesAsync` returns true, and NEVER clear `_tabCloseWorkflows[tab]` while a timed-out release is still in `ContinueTimedOutTabCloseAsync`; the marker is what stops `ActivateTab`/re-close racing a half-disposed editor. Every workflow entry point (`ActivateTab`, `AddNewHomeTab`, `OpenFileInNewTab`, `Window_Drop`, `NewTab_Click`, `Nav*`, `NavigateActiveTabToFile`, Ctrl+T/W/Tab) must keep its `_windowCloseWorkflowActive || _navigationWorkflowActive || _tabCloseWorkflows.Count > 0` guard — creation paths refuse silently mid-workflow.
- AutomationIds on chrome (`NavBackButton`, `NavForwardButton`, `NavHomeButton`, `MinimizeButton`, `MaximizeButton`, `CloseButton`, `NewTabButton`, `TabStrip`, `AppTab`, `TabCloseButton`) are load-bearing for the UIA smoke scripts in `tools/` — keep them stable.
- `MainWindow` ctor order matters: `InitializeAppWindow` (SetTitleBar needs the element) → settings/theme apply → `RegisterWindow` → first home tab.
